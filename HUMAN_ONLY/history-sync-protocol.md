# Plant Talk BLE 历史同步协议 v1

该协议用于 ESP32 将 Flash 中的五分钟定时采样记录及按需追加样本增量同步到 iOS App。实时读数协议保持不变。

## Characteristic

| 用途 | UUID | 属性 |
|---|---|---|
| 实时数据 | `7A1E0002-7C6D-4A8B-9E1F-2D3C4B5A6000` | Read / Notify |
| 历史控制 | `7A1E0003-7C6D-4A8B-9E1F-2D3C4B5A6000` | Write |
| 历史数据 | `7A1E0004-7C6D-4A8B-9E1F-2D3C4B5A6000` | Notify |

所有多字节整数均为 little-endian。历史通知固定为 20 字节，无需依赖更大的协商 MTU。

## 历史记录通知（type `0x01`）

| 字节 | 类型 | 含义 |
|---|---|---|
| 0 | UInt8 | 协议版本，固定为 `1` |
| 1 | UInt8 | 包类型，记录为 `0x01` |
| 2 | UInt8 | 有效标志：bit0 = SHT31，bit1 = BH1750，bit2 = 时间为重启后的估算值 |
| 3 | UInt8 | CRC-8/ATM |
| 4–7 | UInt32 | 单调递增序号 `sequence` |
| 8–11 | UInt32 | UTC Unix 秒时间戳 |
| 12–13 | UInt16 | 土壤湿度 ADC 原始值 |
| 14–15 | Int16 | 温度 × 100 |
| 16–17 | UInt16 | 空气湿度 × 100 |
| 18–19 | UInt16 | 光照 lux，最大 65535 |

CRC 使用多项式 `0x07`、初值 `0`，计算时跳过 byte 3。

`sequence` 从 1 开始，每成功写入一条 Flash 记录递增一次。App 将 `(device_id, sequence)` 设为唯一键，因此重传不会形成重复记录。

## 批次结束通知（type `0x02`）

同样固定为 20 字节，并使用相同 CRC：

| 字节 | 类型 | 含义 |
|---|---|---|
| 0 | UInt8 | 版本 `1` |
| 1 | UInt8 | `0x02` |
| 2 | UInt8 | 本批实际发送的记录数，范围 `0...64` |
| 3 | UInt8 | CRC-8/ATM |
| 4–7 | UInt32 | 本批最后一个序号；空批次等于请求游标 |
| 8–11 | UInt32 | 设备上尚未发送的记录数 |
| 12–15 | UInt32 | 设备当前最新序号 |
| 16–19 | UInt32 | 本批第一条序号；空批次为 `0` |

App 必须同时核对本批的首序号、末序号、记录数以及实际收到的连续序号，全部一致后才可
写入并推进游标。首序号允许大于“请求游标 + 1”，因为环形存储覆盖、LittleFS 损坏或 NVS
预留区间可能造成源端序号空洞；但这个跳跃必须由批次结束包明确声明。这样可以区分
“ESP32 本来就没有这几条”和“ESP32 声称发送了、但 BLE 在批次开头漏掉了几条”。

错误通知使用 type `0x03`，错误码为 bytes 4–5 的 UInt16。

## App 控制命令

请求游标后的记录，共 8 字节：

| 字节 | 内容 |
|---|---|
| 0 | 版本 `1` |
| 1 | 命令 `0x10` |
| 2–5 | App 已持久化的最后序号，UInt32 |
| 6–7 | 本批最大记录数，当前为 64 |

确认 SQLite 已持久化，共 6 字节：

| 字节 | 内容 |
|---|---|
| 0 | 版本 `1` |
| 1 | 命令 `0x11` |
| 2–5 | 已持久化到的序号，UInt32 |

iPhone 校时命令同样为 6 字节：

| 字节 | 内容 |
|---|---|
| 0 | 版本 `1` |
| 1 | 命令 `0x12` |
| 2–5 | 当前 UTC Unix 秒，UInt32 |

立即采样命令为 2 字节：

| 字节 | 内容 |
|---|---|
| 0 | 版本 `1` |
| 1 | 命令 `0x13` |

ESP32 收到 `0x13` 后会立刻读取传感器、发送一条新的实时数据通知，并把该读数作为**额外历史样本**写入 Flash。它不会改写定时器的 `lastSampleTime`，因此原有五分钟采样节拍保持不变；下一次定时采样仍按原来的节拍到来。App 只有在控制写入成功后又收到一条新的实时通知时，才将本次请求视为成功。

## 流程与故障恢复

1. App 发现控制 characteristic 后先发送 `0x12` 校时，再订阅历史通知并从 SQLite 读取该设备的最后游标。
2. App 请求游标后的最多 64 条记录。
3. ESP32 顺序通知记录，最后发送包含首序号、末序号和实际记录数的批次结束包，然后暂停。
4. App 校验 CRC、声明范围、实际数量和连续序号，在 GRDB 单个事务中批量写入记录并更新游标。
5. 只有事务提交成功后，App 才发送 ACK；若仍有记录，再请求下一批。
6. 断线、App 退出或写入失败时不推进游标。下次连接会重传，唯一键负责去重。

设备断电期间不会产生记录：恢复后的下一条记录仍使用紧邻的下一个序号，只是时间戳存在
较大间隔。这属于采样源端的时间缺口，不是传输丢包，不触发重传。若批次完整性校验失败，
App 不发送 ACK；后续手动重试、下一次实时采样触发同步或重新连接时会从原游标重传。

ESP32 不应无节制连续推送全部历史；必须等待 App 的下一批请求，以避免 BLE 通知速度超过 SQLite 写入速度。

固件把完整的 20 字节历史包直接存入 `/history.bin`。物理槽位为
`(sequence - 1) % capacity`，启动时扫描 CRC 正确的槽位恢复最早、最新和下一个序号，
因此不需要每次采样额外重写元数据文件。批次读取与 Flash 写入都在 Arduino 主循环中完成，
BLE `onWrite` 回调只把命令放进 FreeRTOS 队列。

为防止 LittleFS 损坏并格式化后 `sequence` 回到 1，固件在独立 NVS 中一次预留 1024 个
序号。正常情况下只有用完一个预留区间才写一次 NVS；若历史文件丢失，则从预留边界继续，
允许序号有空洞但绝不复用。App 允许每个批次的首条记录跨过这种空洞。

## Flash 容量边界

五分钟采样每天 288 条，每年 105,120 条。若 Flash 中使用紧凑的固定 20 字节记录：

- 完整 4 MiB 理论上约 209,715 条，即约 728 天；
- 但 4 MB 是芯片总 Flash，还要容纳固件、NVS、OTA 分区和 LittleFS；
- 若最终只分配 1.5 MiB 给历史区，约可保存 273 天。
- 当前默认 partition 的实际文件系统区为 `0x160000` 字节，固件再保留 64 KiB，
  可用 68,812 个记录槽，约 238 天。

以上是只按五分钟定时采样计算的基准值；每次 `0x13` 立即采样也会额外占用一个记录槽，因此频繁手动刷新会相应缩短可保留的历史时长。

烧录时必须确认实际 partition table。手机连接后会自动校时；持续供电期间时间准确。
重启后，固件会从最后一条记录加五分钟恢复近似时间，并设置 bit2；断电持续时间未知，
因此无人值守且要求断电后仍保持准确时间时，仍需要 DS3231 RTC 或可用的 NTP 校时。
